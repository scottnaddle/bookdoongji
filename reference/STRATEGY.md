# 수험서 eBook 플랫폼 기술 전략

- **작성일:** 2026-10-18
- **문서 성격:** 원본 리서치 기반 오리지널 구현 전략 (웹 + 모바일 앱)
- **대상:** 수험서·학습서 중심의 웹 커머스와 iOS/Android eBook 리더를 통합 제공하는 신규 플랫폼
- **기본 가정:** 초기 개발팀은 제품 책임자 1명, 디자이너 1명, 웹·백엔드 개발자 2~3명, 모바일 개발자 2명, QA 1명 수준의 소규모 팀으로 구성한다.

## A. 웹 플랫폼 전략

## 1. 기술 스택 선정

### 1.1 아키텍처 원칙

초기에는 마이크로서비스보다 **모듈형 모놀리스(modular monolith)**를 채택한다. 주문, 결제, 라이선스, 포인트처럼 트랜잭션 일관성이 중요한 영역을 하나의 백엔드와 관계형 데이터베이스에서 관리하고, 검색·콘텐츠 변환·알림처럼 독립성이 높은 작업만 별도 워커로 분리한다.

핵심 원칙은 다음과 같다.

- 웹과 앱이 동일한 백엔드 API와 도메인 모델을 사용한다.
- 도서 메타데이터와 판매 상품을 분리한다.
- 주문·결제·포인트 원장은 변경 이력을 보존하는 방식으로 설계한다.
- 구매와 실제 열람 권한을 분리해 환불, 대여 만료, 구독 해지에 대응한다.
- 원본 eBook 파일은 공개 URL로 제공하지 않고, 인증된 단기 URL과 DRM 또는 암호화 패키지로 전달한다.
- 검색, 이미지 변환, 알림, 라이선스 발급은 비동기 작업으로 분리한다.
- 초기 운영 복잡도를 억제하되, 도메인 경계를 명확히 해 향후 서비스 분리가 가능하도록 한다.

### 1.3 Next.js 선정 판단

참고 대상이 Next.js App Router와 CDN을 사용했다는 사실 자체를 모방 근거로 삼지 않는다. 신규 플랫폼에서도 Next.js를 선택하는 이유는 다음과 같다.

- 상품 상세와 카테고리 페이지에 SEO와 서버 렌더링이 필요하다.
- React Native 앱과 TypeScript 타입, API 클라이언트, 도메인 규칙을 공유할 수 있다.
- React 기반 인력 채용과 유지보수가 비교적 용이하다.
- 서버 컴포넌트를 활용해 브라우저로 전달되는 JavaScript를 줄일 수 있다.
- 이미지 최적화, 라우팅, 메타데이터 생성, 캐시 제어를 하나의 프레임워크에서 처리할 수 있다.

단, Next.js 서버 액션에 핵심 비즈니스 로직을 직접 종속시키지 않는다. 주문, 결제, 라이선스, 포인트 로직은 독립된 백엔드 API에 둔다. 그래야 모바일 앱과 운영 콘솔이 같은 로직을 사용할 수 있다.

### 1.4 데이터 및 보안 기준

- 개인정보, 주문, 결제, 라이선스 데이터는 저장 시 암호화한다.
- 카드 번호를 자체 저장하지 않고 PG가 발급한 결제수단 토큰만 보관한다.
- 관리자 작업과 포인트 조정은 감사 로그를 남긴다.
- 웹훅은 서명 검증, 재전송 처리, 멱등성 키를 적용한다.
- 다운로드 URL은 짧은 만료 시간과 사용자·기기·라이선스 범위 제한을 둔다.
- 관리자와 출판사 계정에는 다중 인증을 적용한다.
- 백업 복구 목표를 정의하고 정기적으로 복구 훈련을 수행한다.
- 저작권 보호 파일과 서비스 로그의 접근 권한을 최소화한다.
- 결제 완료 화면이 아니라 서버 간 결제 확인을 최종 진실 원천으로 사용한다.

## 2. MVP 범위 정의

### 2.1 판매 모델별 결정

| 판매 모델 | MVP 포함 여부 | 결정 |
|---|---:|---|
| 소장 | 포함 | 플랫폼의 가장 단순하고 핵심적인 거래 모델이다. 결제 완료 후 지속적인 열람 권한을 부여한다. |
| 대여 | 포함 | 수험서의 이용 기간과 잘 맞고, 만료일 기반 라이선스 모델을 초기에 검증할 수 있다. |
| 무료 | 포함 | 결제 없이 가입, 서재 등록, 다운로드, 리더 사용까지 전체 흐름을 시험할 수 있다. 체험 전환에도 유리하다. |
| 구독패스 | 제외 | 반복 결제, 갱신, 유예 기간, 해지, 환불, 포함 도서 변경, 정산 등 복잡한 상태 관리가 필요하다. Phase 3에서 도입한다. |
| 스마트 eBook | 제외 | 문항 구조화, OMR UI, 자동 채점, 정답·해설 데이터, 시험 상태 저장, 오답노트 생성이 필요하다. 콘텐츠 제작 도구까지 필요하므로 Phase 3로 연기한다. |

### 2.2 MVP에 포함할 핵심 범위

- 이메일 또는 소셜 로그인
- 성인 여부 및 필수 약관 동의
- 카테고리·검색 기반 도서 탐색
- 상품 상세, 미리보기, 소장·대여·무료 옵션 표시
- 찜과 장바구니
- 쿠폰 적용
- 웹 PG 결제
- 주문·결제 결과 확인
- 소장 및 기간제 열람 권한 발급
- 내 서재와 주문 내역
- 앱용 보호 콘텐츠 다운로드 API
- 기본 운영자 기능
  - 도서·저자·출판사 메타데이터 관리
  - 상품·가격·판매 기간 관리
  - 파일 등록 및 변환 상태 확인
  - 주문·결제·환불 조회
  - 쿠폰 발행
  - 수동 라이선스 조정과 감사 로그
- 기본 고객지원 기능
  - 거래번호 조회
  - 환불 요청 접수
  - 다운로드·라이선스 재발급

### 2.3 포인트 범위 조정

포인트는 MVP의 필수 수단이 아니라 P1 기능으로 둔다. 선불 충전금은 전자금융·회계·환불·소멸·부채 관리 부담이 크기 때문이다.

MVP에서는 우선 다음 방식이 안전하다.

- 프로모션성 무상 포인트만 지원하거나 쿠폰으로 대체한다.
- 유상 충전 기능은 별도 법률·회계 검토 후 활성화한다.
- 포인트를 도입한다면 유상 충전금과 무상 적립금을 서로 다른 원장과 사용 우선순위로 관리한다.
- 현금성 잔액과 이벤트성 혜택을 UI 및 약관에서 명확히 구분한다.

### 2.4 MVP 성공 기준

- 결제 성공 주문의 라이선스 발급 성공률 99.9% 이상
- 동일 결제의 중복 주문·중복 차감 0건
- 권리 보유 사용자의 앱 다운로드 성공률 99% 이상
- 대여 만료 후 신규 다운로드와 열람 권한이 정책대로 제한될 것
- 무료 도서 등록부터 앱 열람까지 막힘 없이 완료될 것
- 상품 상세 핵심 콘텐츠의 모바일 웹 성능 지표가 목표 범위에 들어올 것
- 고객지원 담당자가 관리자 도구에서 주문·결제·권리 상태를 한 번에 추적할 수 있을 것

## 4. 데이터 모델 개요

### 4.1 모델링 원칙

`book`은 지적 콘텐츠와 서지 정보를 나타내고, `product`와 `SKU`는 판매 조건을 나타낸다. 사용자가 결제한 주문과 실제 열람 권한은 별도 엔티티로 관리한다.

예를 들어 같은 책에 다음 SKU가 공존할 수 있다.

- 영구 소장 SKU
- 90일 대여 SKU
- 특정 날짜까지 유효한 대여 SKU
- 무료 체험 SKU
- 향후 구독 플랜에 포함되는 SKU

이 분리는 가격 변경, 판본 교체, 대여 만료, 환불, 구독 상품군 변경을 안전하게 처리하는 기반이다.

### 4.2 핵심 엔티티

| 엔티티 | 주요 필드 | 관계 및 역할 |
|---|---|---|
| `publisher` | id, name, contract_status | 여러 도서와 권리 계약을 가진다. |
| `author` | id, display_name | `book_author`를 통해 도서와 다대다 관계를 가진다. |
| `book` | id, title, subtitle, description, isbn, publisher_id, publication_date, edition | 공통 서지 정보의 중심이다. 가격이나 판매 방식은 포함하지 않는다. |
| `book_author` | book_id, author_id, role, sort_order | 저자·감수자·번역자 등의 역할과 표시 순서를 관리한다. |
| `category` | id, parent_id, name, slug, sort_order | 자기 참조 계층을 구성한다. 공개 URL은 숫자 ID보다 고유 슬러그를 우선한다. |
| `book_category` | book_id, category_id, is_primary | 도서와 카테고리의 다대다 관계다. |
| `content_asset` | id, book_id, version, format, storage_key, checksum, drm_profile, status | 원본·변환본·미리보기 파일을 관리한다. |
| `product` | id, book_id, name, status, sales_start_at, sales_end_at | 고객에게 노출되는 판매 단위다. |
| `sku` | id, product_id, sale_type, list_price, sale_price, currency, rental_policy_id | 소장·대여·무료·구독 등 구체적인 구매 옵션이다. |
| `rental_policy` | id, duration_type, duration_days, fixed_end_at, offline_grace_hours | 상대 기간 또는 고정 만료일 등 대여 조건을 정의한다. |
| `user` | id, status, email, display_name, created_at | 내부 사용자 식별자다. 소셜 공급자 ID와 분리한다. |
| `user_identity` | id, user_id, provider, provider_subject | OAuth/OIDC 소셜 계정과 내부 사용자를 연결한다. |
| `device` | id, user_id, platform, device_public_key, last_seen_at, revoked_at | 콘텐츠 다운로드와 오프라인 라이선스 발급 대상을 관리한다. |
| `cart` | id, user_id, status | 활성 장바구니를 나타낸다. |
| `cart_item` | cart_id, sku_id, quantity, price_snapshot | SKU 선택과 당시 가격 정보를 담는다. eBook 수량은 원칙적으로 1이다. |
| `order` | id, user_id, status, subtotal, discount_total, point_total, payable_total, currency | 구매 의사와 금액 합계를 기록한다. |
| `order_item` | id, order_id, sku_id, product_snapshot, unit_price, discount_amount | 주문 당시 상품명·조건·가격을 스냅샷으로 보존한다. |
| `payment` | id, order_id, provider, method, status, provider_transaction_id, amount | PG 또는 앱스토어의 결제 거래를 기록한다. 한 주문에 재시도 거래가 여러 건 존재할 수 있다. |
| `payment_event` | id, payment_id, event_type, payload_hash, occurred_at | 승인·취소·웹훅·영수증 검증 이력을 보존한다. |
| `refund` | id, payment_id, order_item_id, amount, status, reason | 전체 또는 부분 환불을 관리한다. |
| `coupon` | id, code, discount_type, value, usage_limit, starts_at, ends_at | 할인 규칙의 정의다. |
| `coupon_rule` | coupon_id, target_type, target_id, min_order_amount | 특정 상품·카테고리·사용자군 등 적용 조건을 정의한다. |

| `library_item` | id, user_id, book_id, acquisition_type, entitlement_id, added_at | 사용자의 서재 표시 단위다. 실제 권리 상태는 연결된 entitlement에서 계산한다. |
| `entitlement` | id, user_id, book_id, source_type, source_id, valid_from, valid_to, status | 소장·대여·구독·무료 권리를 하나의 인터페이스로 통합한다. |
| `download_license` | id, entitlement_id, device_id, content_asset_id, issued_at, expires_at | 특정 기기와 콘텐츠 버전에 대한 오프라인 열람 권한이다. |
| `annotation` | id, user_id, book_id, asset_version, page_ref, type, payload, revision | 필기·형광펜을 동기화한다. 충돌 처리를 위한 revision을 둔다. |
| `audit_log` | id, actor_id, action, target_type, target_id, before, after | 관리자와 시스템의 중요 변경을 추적한다. |

### 4.3 핵심 관계

```text
Publisher 1 ── N Book
Book N ── N Author
Book N ── N Category
Book 1 ── N ContentAsset
Book 1 ── N Product
Product 1 ── N SKU

User 1 ── N Order
Order 1 ── N OrderItem
Order 1 ── N Payment
Payment 1 ── N PaymentEvent
Payment 1 ── N Refund

User 1 ── N Entitlement
OrderItem 1 ── 0..1 Entitlement

Subscription 1 ── N Entitlement
Entitlement N ── 1 Book

User 1 ── N LibraryItem

User 1 ── N Device
Entitlement 1 ── N DownloadLicense

User 1 ── 1 PointAccount
PointAccount 1 ── N PointLedger
```

### 4.4 주문·결제·권리 상태 흐름

1. 서버가 SKU 판매 가능 여부와 현재 가격을 검증한다.
2. `order`와 `order_item`을 `PENDING` 상태로 생성한다.
3. 결제 시도마다 `payment`를 생성한다.
4. PG 또는 앱스토어 결과를 서버에서 검증한다.
5. 결제가 확정되면 주문을 `PAID`로 전환한다.
6. 권리 발급 작업이 `entitlement`와 `library_item`을 생성한다.
7. 권리 발급 실패 시 주문을 잃지 않고 재처리 큐로 보낸다.
8. 환불이 확정되면 해당 권리를 취소하거나 유효 기간을 조정한다.
9. 이미 다운로드한 콘텐츠는 정책에 따라 다음 온라인 검증 또는 오프라인 유예 기간 종료 시 잠근다.

결제 상태와 권리 상태를 하나의 필드로 합치지 않는다. 결제는 성공했지만 권리 발급이 지연될 수 있기 때문이다.

### 4.5 필기 데이터 전략

- 필기는 원본 PDF 자체를 변경하지 않고 별도 레이어로 저장한다.
- 페이지 번호만 사용하지 말고 콘텐츠 버전과 안정적인 페이지 식별자를 함께 저장한다.
- 선, 색상, 굵기, 도구, 좌표, 생성 시각, 수정 시각을 구조화한다.
- 장시간 필기는 로컬 데이터베이스에 먼저 기록하고 비동기로 동기화한다.
- 이벤트 로그와 주기적 스냅샷을 조합해 복구 성능을 확보한다.
- 콘텐츠 판본 변경 시 필기 좌표 호환 여부를 검사하고 자동 이전이 불가능하면 기존 버전을 유지한다.

- 필기·형광펜 동기화 API

- 스토어·웹 구독 상태가 중복 권리 없이 통합되어야 한다.
- 정답 변경과 문항 버전 변경 이력이 보존되어야 한다.
- 시험 중 앱 종료나 네트워크 단절이 발생해도 답안이 복원되어야 한다.

### 6.2 최종 선정

**React Native + Expo 개발 빌드(Prebuild 포함)를 최종 선정한다.**

단, Expo Go만 사용하는 순수 관리형 앱으로 제한하지 않는다. 핵심 리더와 스타일러스 기능은 다음과 같이 네이티브 계층을 허용한다.

- iOS: PencilKit 또는 Metal 기반 네이티브 리더·필기 뷰
- Android: MotionEvent의 stylus 정보, S Pen 호버·버튼 이벤트, 저지연 캔버스
- 공통 렌더링이 필요할 경우: React Native Skia 또는 C++ 기반 공유 코어 검토
- React Native: 인증, 서재, 다운로드 관리, 카테고리, 검색, 상품 상세, 설정, 분석 이벤트
- 네이티브 모듈: 필기, PDF 렌더링, 암호화·복호화, 안전한 키 보관, 백그라운드 다운로드

### 6.3 선정 이유

- 웹과 TypeScript 타입, API 클라이언트, 오류 모델, 검증 스키마, 가격 표시 규칙을 공유할 수 있다.
- 하나의 제품팀이 iOS와 Android의 공통 기능을 빠르게 제공할 수 있다.
- Expo의 빌드·업데이트·딥링크·알림 도구를 활용하면서 필요한 네이티브 기능은 직접 확장할 수 있다.
- 스마트 OMR과 시험 화면은 React Native에서 충분히 구현 가능하다.
- 필기 성능이 중요한 경로만 네이티브로 최적화해 비용과 품질 사이의 균형을 맞출 수 있다.

### 6.4 기술적 제한과 대응

React Native를 선택했다고 해서 웹 UI 컴포넌트를 그대로 앱에 복사하지 않는다. 실제 공유 대상은 다음에 집중한다.

- API 스키마와 생성 클라이언트
- 도메인 타입
- 가격·대여 만료·권리 상태 계산
- 입력 검증
- 디자인 토큰
- 국제화 리소스의 구조
- 분석 이벤트 이름
- 기능 플래그 정의

필기 엔진은 앱 개발 초기에 별도 기술 검증을 수행한다. 다음 조건을 만족하지 못하면 필기 화면만 네이티브 구현 비중을 높인다.

- Apple Pencil 및 S Pen에서 체감 지연이 낮을 것
- 손바닥 오작동 방지가 안정적일 것
- 긴 필기 세션에서 메모리 사용량이 통제될 것
- 확대·축소 중에도 획 좌표가 정확할 것
- 수천 개 획이 있는 페이지에서도 렌더링 성능을 유지할 것
- 앱 강제 종료 후에도 최근 획이 복구될 것

다음 기능은 Phase 2 이후로 연기한다.

- 스마트 OMR
- 자동 채점
- 시험 모드와 타이머
- 자동 오답노트
- 마스킹 펜
- 제스처 기반 텍스트 선택
- 다중 문서 분할 보기
- 고급 스크랩과 원문 링크
- 실시간 협업
- 외부 PDF 내보내기
- 구독패스
- 고급 학습 분석

### 7.3 연기 이유

- 스마트 OMR은 앱 UI만으로 완성되지 않으며 문항 좌표, 정답, 해설, 판본을 관리하는 콘텐츠 공급망이 필요하다.
- 시험 모드는 중단 복구, 시간 조작 방지, 자동 저장 등 별도 신뢰성 요건을 가진다.
- 마스킹과 제스처 인식은 PDF 텍스트 레이어 품질과 좌표 정규화에 크게 의존한다.
- 고급 기능을 동시에 개발하면 다운로드, 오프라인 권리, 필기 저장 같은 기반 기능의 안정화가 늦어진다.
- MVP에서는 사용자가 실제로 구매한 콘텐츠를 안정적으로 내려받고 읽고 필기하는 경험이 우선이다.

### 7.4 앱 MVP 품질 기준

- 다운로드 중 앱이 종료되어도 재개할 수 있어야 한다.
- 다운로드 파일의 체크섬과 서명을 검증해야 한다.
- 대여 만료 및 환불된 권리가 정책대로 반영되어야 한다.
- 필기 입력은 네트워크와 관계없이 즉시 로컬에 저장되어야 한다.
- 동기화 충돌로 기존 필기를 무음 삭제하지 않아야 한다.
- 태블릿 회전, 멀티태스킹, 백그라운드 전환 후 읽던 위치가 복원되어야 한다.
- 최소 지원 OS와 대표 iPad·갤럭시 탭에서 성능 테스트를 통과해야 한다.

## 8. 웹-앱 공유 전략

### 8.1 단일 백엔드 API

웹과 앱은 하나의 도메인 백엔드와 데이터 모델을 사용한다. 채널별로 주문 규칙을 복제하지 않는다.

권장 API 영역은 다음과 같다.

- 인증과 계정
- 카탈로그와 검색
- 가격과 프로모션
- 장바구니와 주문
- 결제 상태
- 앱스토어 영수증 검증
- 서재와 권리
- 기기와 다운로드 라이선스
- 필기와 읽기 위치 동기화
- 푸시 토큰과 알림 설정

외부 인터페이스는 REST/OpenAPI를 우선한다. 목록 화면의 조합 요청이 과도해지면 웹·앱별 BFF를 추가할 수 있지만, 주문과 권리의 원본 로직은 공통 도메인 서비스에 유지한다.

### 8.2 인증 공유

#### 기본 방식

- OAuth 2.1 및 OpenID Connect 호환 흐름을 사용한다.
- 앱은 Authorization Code Flow with PKCE를 사용한다.
- 웹은 서버가 관리하는 `HttpOnly`, `Secure`, `SameSite` 쿠키 세션을 사용한다.
- 앱은 짧은 수명의 access token과 회전식 refresh token을 사용한다.
- refresh token은 iOS Keychain과 Android Keystore 기반 보안 저장소에 보관한다.
- 웹과 앱 모두 동일한 내부 `user_id`와 권한 체계를 사용한다.

#### 통합 방안

인증 서버가 동일한 사용자와 세션 계열을 관리하되, 웹과 앱의 자격 증명 저장 방식은 분리한다.

- 웹 브라우저에 장기 refresh token을 JavaScript 접근 가능한 저장소로 노출하지 않는다.
- 앱의 refresh token은 기기·클라이언트와 결합하고 재사용 탐지를 적용한다.
- 소셜 로그인 공급자가 달라도 검증된 이메일만으로 자동 병합하지 않는다.
- 계정 연결은 기존 계정 재인증을 요구한다.
- 비밀번호 변경, 탈퇴, 의심 활동 발생 시 토큰 계열을 폐기한다.
- 콘텐츠 라이선스는 일반 API 토큰과 별도로 짧은 수명의 기기별 증명서를 사용할 수 있다.

### 8.3 모노레포 구조

```text
apps/
  web/                 Next.js 고객용 웹
  admin/               운영자 웹
  mobile/              React Native + Expo 앱
  api/                 NestJS API
  worker/              비동기 작업 워커

packages/
  api-client/          OpenAPI 기반 생성 클라이언트
  contracts/           요청·응답 타입과 검증 스키마
  domain/              가격·권리·기간 계산 등 순수 로직
  design-tokens/       색상·타이포그래피·간격·모션 토큰
  analytics/           이벤트 이름과 공통 속성
  config/              TypeScript, lint, test 설정
  localization/        메시지 키와 번역 리소스
```

Turborepo와 pnpm workspaces를 사용해 변경 영향 범위만 빌드·테스트한다.

### 8.4 코드 공유 기준

공유해야 하는 코드:

- API 타입과 클라이언트
- 날짜·가격·통화 포맷
- 대여 만료 계산
- 권리 상태 판정
- Zod 검증 스키마
- 분석 이벤트 규약
- 기능 플래그
- 디자인 토큰

플랫폼별로 분리해야 하는 코드:

- 웹 DOM 컴포넌트와 React Native 화면
- 결제 UI
- 딥링크 처리
- 다운로드와 파일 시스템
- 보안 저장소
- PDF 렌더러
- 스타일러스 입력과 필기 캔버스
- 앱 생명주기와 백그라운드 작업

### 8.5 디자인 시스템 공유

디자인 토큰은 JSON 또는 토큰 전용 패키지를 단일 원천으로 사용한다.

- 브랜드 색상과 의미 기반 색상
- 타이포그래피 단계
- 간격, 모서리, 그림자
- 아이콘 크기
- 모션 지속 시간
- 접근성 대비 기준
- 상태 색상
- 태블릿 및 모바일 브레이크포인트 개념

웹과 앱은 토큰을 각 플랫폼 형식으로 변환한다. UI 구현을 강제로 동일하게 만들지는 않는다. 탐색, 뒤로 가기, 시스템 메뉴, 구매 화면은 각 플랫폼 관례를 따른다.

### 8.6 푸시 알림 전략

- Android와 공통 라우팅에는 FCM을 사용한다.
- iOS 전송은 APNs를 기반으로 하며 FCM을 통합 게이트웨이로 사용할 수 있다.
- 사용자별로 여러 기기의 push token을 관리한다.
- 토큰은 앱 재설치·갱신에 따라 업데이트하고 무효 토큰은 제거한다.
- 알림 종류별 수신 동의를 관리한다.
- 거래성 알림과 마케팅 알림을 분리한다.
- 딥링크에는 민감 정보를 직접 포함하지 않고 서버 조회용 식별자만 사용한다.

우선 알림 대상:

- 대여 만료 예정
- 결제 및 환불 결과
- 다운로드 또는 콘텐츠 업데이트 완료
- 구독 갱신 및 결제 실패
- 보안상 중요한 새 기기 등록
- 사용자가 동의한 신간·할인 소식

### 8.7 분석 및 관찰성 공유

웹과 앱은 동일한 이벤트 명세를 사용한다.

- `catalog_viewed`
- `product_viewed`
- `purchase_started`
- `purchase_completed`
- `library_item_opened`
- `download_completed`
- `reader_session_started`
- `annotation_created`

이벤트에는 불필요한 개인정보나 필기 원문을 넣지 않는다. 주문·결제·라이선스에는 공통 상관관계 ID를 부여해 고객지원과 장애 분석에서 전체 흐름을 추적한다.

이유는 다음과 같다.

- API와 제품 기능은 양 플랫폼에서 동시에 검증해야 시장과 운영이 분절되지 않는다.
- 수험 학습에서는 iPad와 Android 태블릿 모두 중요하므로 한 플랫폼을 장기간 제외하기 어렵다.
- 반면 스타일러스와 기기 파편화가 큰 Android까지 모든 실험을 동시에 수행하면 작은 팀의 디버깅 비용이 급증한다.
- 초기 필기 엔진 검증은 하드웨어 변수가 상대적으로 제한적인 iPad에서 먼저 진행하는 것이 효율적이다.
- 공통 기능은 React Native로 병행하고, iOS 필기 경로를 약 2~4주 앞서 안정화한 뒤 Android 스타일러스 최적화를 따라가게 한다.
- 공개 출시는 두 플랫폼의 핵심 품질 기준이 충족된 시점에 맞춘다.

다만 Android 안정화가 전체 출시를 장기간 지연시킨다면 제한된 iOS 베타 또는 소프트 론칭을 먼저 할 수 있다. 이 경우 Android 출시 일정과 지원 범위를 명확히 공지하고 기능 격차를 최소화한다.

## 10. 원칙 선언

### 10.1 오리지널 구현 원칙

이 프로젝트는 참고 서비스의 사업 구조와 일반적인 eBook·커머스 기능에서 아이디어를 얻되, 결과물은 독립적인 브랜드와 제품으로 개발한다.

- 원본 서비스의 브랜드명, 상표, 도메인과 혼동되는 명칭
- 슬로건, 광고 문구, 버튼 문구, 설명문 등 고유한 카피

- 도서 표지, 배너, 아이콘, 일러스트, 스크린샷
- 로고, 색상명, 고유 팔레트, 타이포그래피 조합
- 화면 배치와 시각적 표현을 실질적으로 재현한 UI
- 앱의 온보딩·오류·결제·학습 안내 문구
- 비공개 API, JavaScript 번들, 데이터 구조 또는 인증 흐름의 역공학 결과
- 원본이 독자적으로 제작한 분류 체계, 기획전 구성, 추천 문구의 일괄 복제

기능 아이디어는 다음과 같이 일반화해 독립적으로 설계한다.

- “대여”는 자체 계약과 정책에 따라 새로운 기간 모델을 정의한다.
- “구독”은 자체 플랜, 가격, 포함 도서와 해지 정책을 만든다.
- “스마트 학습”은 독자적인 문항 포맷과 UX 연구를 통해 구현한다.
- 카테고리 구조는 확보한 합법적 도서 공급 데이터와 사용자 조사에 근거해 작성한다.
- 디자인 시스템은 새로운 브랜드 전략과 접근성 기준에서 출발한다.
- UI 카피는 자체 편집 기준과 법률 검토를 거쳐 작성한다.

### 10.2 상품 및 콘텐츠 권리

- 도서 파일, 표지, 소개, 목차, 미리보기, 저자 정보는 출판사 또는 적법한 유통 파트너에게 제공·사용 권한을 받아야 한다.
- ISBN과 공개 서지 정보라도 데이터베이스 전체를 무단 복제하지 않는다.
- 계약서에는 판매 방식, 지역, 기간, 지원 기기, DRM, 미리보기 범위, 환불, 정산, 구독 포함 여부를 명시한다.
- 스마트 문항용 정답·해설과 좌표 데이터의 소유권 및 2차적 저작물 권리를 명확히 한다.
- 무료 자료도 “무료로 접근 가능”하다는 이유만으로 재배포하지 않는다.
- 사용자 필기의 소유권, 저장 기간, 탈퇴 시 처리, 내보내기 범위를 약관에 명시한다.
- 저작권 침해 신고와 콘텐츠 중단 요청을 처리하는 절차를 마련한다.

### 10.3 상표권 및 부정경쟁 리스크 회피

- 출시 전에 브랜드명, 앱 이름, 도메인, 주요 로고에 대한 상표 검색을 수행한다.
- 경쟁 서비스와 발음·철자·시각적 인상이 유사한 이름을 피한다.
- “공식”, “제휴”, “인증” 등 관계를 오인하게 하는 표현을 사용하지 않는다.
- 앱 아이콘, 스토어 설명, 검색 키워드에 경쟁 브랜드를 부당하게 이용하지 않는다.
- 경쟁 서비스와 혼동될 가능성이 있는 화면, 컬러 조합, 캐릭터, 배지를 사용하지 않는다.
- 최종 브랜드와 주요 UI는 출시 전 지식재산권 전문가의 검토를 받는다.

### 10.4 앱스토어 결제 정책

디지털 도서, 구독, 앱 내에서 소비되는 학습 기능은 원칙적으로 Apple App Store와 Google Play의 인앱결제 정책 적용 가능성이 높다. 따라서 다음을 기본 방침으로 한다.

- 앱에서 디지털 콘텐츠를 직접 판매하면 각 스토어가 요구하는 인앱결제 시스템을 구현한다.
- 앱 내부 웹뷰에 일반 PG 결제를 넣어 인앱결제를 우회하지 않는다.
- 외부 결제 링크, 가격 안내, 구매 유도 문구는 국가·스토어·앱 유형별 최신 정책과 허용된 권리 범위에서만 제공한다.
- 리더 앱 예외, 외부 링크 허용 프로그램, 지역별 대체 결제 규정은 자동 적용된다고 가정하지 않는다.
- 웹 구매 상품을 앱에서 열람하는 구조도 스토어의 리더 앱 요건과 메타데이터 정책을 별도로 검토한다.
- 인앱결제 상품 ID를 내부 SKU와 분리하고 서버에서 매핑한다.
- 클라이언트의 성공 화면만 신뢰하지 않고 Apple·Google 영수증 및 서버 알림을 검증한다.
- 환불, 취소, 구독 유예, 청구 재시도, 가족 공유 여부를 entitlement에 반영한다.
- 스토어 가격과 웹 가격이 다를 경우 사용자에게 오해가 없도록 표시하고 차별적 유도 문구를 피한다.
- 앱 심사 계정에는 실제로 탐색·구매·서재·리더 흐름을 확인할 수 있는 테스트 콘텐츠와 설명을 제공한다.
- 계정 생성 기능이 있다면 앱 안에서 계정 삭제를 요청할 수 있는 경로를 제공한다.
- 결제 정책은 수시로 변경될 수 있으므로 출시 전과 주요 업데이트 전마다 Apple·Google의 최신 공식 지침을 재검토한다.

### 10.5 보안과 DRM의 한계

DRM은 무단 복제를 완전히 제거하는 수단이 아니라 비용과 난이도를 높이는 통제 수단이다. 과도한 DRM으로 정상 사용자의 학습을 방해하지 않도록 다음 균형을 유지한다.

- 기기 수와 오프라인 기간은 계약상 필요한 최소 수준으로 제한한다.
- 기기 교체와 분실에 대응하는 셀프서비스 해제 기능을 제공한다.
- 암호화 키를 앱 코드에 고정 저장하지 않는다.
- 루팅·탈옥 탐지는 보조 신호로만 활용하고 오탐에 대한 복구 절차를 둔다.
- 화면 캡처 제한은 OS 기능과 접근성 요구를 고려한다.
- 필기 데이터는 원본 콘텐츠와 분리해 사용자 데이터로 보호한다.
- DRM 오류로 정상 구매자가 콘텐츠를 잃지 않도록 고객지원과 수동 복구 절차를 마련한다.

### 10.6 최종 선언

본 플랫폼은 참고 서비스의 브랜드, 표현, 자산, 상품 데이터 또는 UI를 복제하는 클론 프로젝트가 아니다. 수험서 전자상거래, 기간제 열람, 디지털 필기, 자동 채점과 같은 일반적인 제품 개념만 참고하고, 브랜드·정보 구조·디자인 시스템·기술 구조·콘텐츠 계약·문항 포맷·앱 UI를 독자적으로 설계한다.

모든 콘텐츠는 적법한 계약과 사용 권한을 기반으로 제공하며, 웹 결제와 앱스토어 결제는 각 채널의 법률·세무·플랫폼 정책을 준수한다. 제품 출시 전에는 지식재산권, 개인정보, 전자상거래, 선불 충전금, 청약철회, 앱스토어 결제 정책을 전문 법률가 및 관련 전문가와 최종 검토한다.
